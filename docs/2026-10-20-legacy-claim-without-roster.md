# 名簿なしで旧データ(`legacy_*`)を本人に付け替える方法(設計案 FZ3)

- 日付: 2026-10-20 / 種別: 設計案(コードなし。実装は FZ3-I、人の承認後)
- 正本: 設計書 v2(改訂5)§4.4・§5.1・§10.3・§11、移行計画 Phase 2、`server/rosterLink.js`、`server/repos/accountsRepo.js`
- **本書の API・表はすべて「案・要承認」**。設計書 v2 にまだ無い。承認までは決定として扱わない。

## 1. 目的と前提

- 2026-10-20 の利用者決定で、名簿の提出とメール照合、複数組織、メール変更などを凍結した。
  残す機能は、登録・ログイン・メール確認・パスワード再設定・アカウント削除・招待リンクによる参加・メンバー一覧・**旧氏名の付け替え**。
- これまで旧データ(部の Web で `projects/*.json` に溜まった反省・軌跡・ロードマップ)は、名簿の「旧名簿の氏名(`legacyName`)」と
  メール照合で本人に付いていた(設計書 §11)。名簿が凍結されると、この付け替えが動かなくなる。
- そこで、名簿なしに「このメンバー = 旧データの ◯◯」を人が一度だけ指定する操作を足す。名簿・メール照合には依存しない。

## 2. 既存の付け替え処理の調査

### 2.1 呼び出しの流れ(名簿経由)

| 入口 | 関数 | 付け替えの呼び方 |
|---|---|---|
| メール確認時 | `rosterLink.linkVerifiedUser` → `linkOne` | 名簿行ごとに `accounts.reattachLegacy({orgId, userId, legacyName: row.legacy_name})` |
| 名簿更新時 | `rosterLink.applyRoster` → `linkOne` | 同上。応答の `reattached` は件数 |

付け替えの本体は **`accountsRepo.reattachLegacy({ orgId, userId, legacyName })`** で、名簿・メールを一切参照しない。
名簿との接点は呼び出し側 `linkOne` だけである。

### 2.2 付け替える表と列(1 トランザクション。件数 `{reflections, sessions, roadmaps}` を返す)

| 対象 | 条件 | 書き換える列 | 備考 |
|---|---|---|---|
| `reflections`(反省) | `legacy_author_name = 氏名` かつ `author_user_id IS NULL` かつ 器(`practice_days.org_id`)がその組織 | `author_user_id` | |
| `rec_sessions`(軌跡) | `legacy_owner_name = 氏名` かつ `owner_user_id IS NULL` かつ 器がその組織 | `owner_user_id` | **現状の取込みでは常に 0 件**。`projectRows.js` が旧形式の軌跡の `legacy_owner_name` を null に固定しているため、旧データの軌跡は組織所有のまま残る(§11)。コードは付け替えるが、現行データでは対象が無い。件数表示の扱いは §8-12 |
| `roadmaps` | `legacy_name = 氏名` かつ `org_id` がその組織 かつ `user_id IS NULL` かつ本人が未所有 | `user_id` | `user_id` が UNIQUE のため、本人が既にロードマップを持てば付け替えない(0 件) |

- 氏名は trim のみ(小文字化・正規化なし)。空は何もしない。
- 他組織の器・既に所有者のいる行は触らない(奪わない)。`legacy_*` 列は来歴として残す。冪等。
- `reflection_progress`・`reflection_comments` は付け替え対象外(進捗は反省 ID に付き、コメントの `author_user_id` は旧データでは NULL のまま)。
  反省が本人のものになれば、進捗は反省経由で本人のものとして見える。コメントの作者は付け替えない(現状どおり。要確認:§8-6)。
- `session_crew`(乗員)の `name` は付け替えない(自由記述の氏名)。現状の名簿経路と同じ。

### 2.3 使い回せるか

- **使い回せる(推奨)**。`reattachLegacy` はそのまま呼べる。新しく要るのは次の 4 つだけ。
  1. 呼び出し元(名簿照合ではなく、組織管理者の操作)。
  2. 候補の氏名の一覧(その組織の、まだ本人のいない `legacy_*` の氏名と件数)。
  3. 取り消し用の逆操作(`reattachLegacy` の逆。§5)。
  4. 実施記録(誰が誰に何を付けたか。取り消しの根拠にもなる)。
- 名簿経路(`linkVerifiedUser`・`applyRoster`)のコードは変更しない。凍結は Web の入口(FZ1)で行われ、サーバの処理は残るため、
  両経路は共存できる(§6)。

## 3. 提案する操作の流れ

- **誰が**: 組織管理者(`org_admins`)。本人による自己申告は提案しない(§8-1)。
- **どこで**: Web のメンバー一覧(組織画面)。メンバーの行に「旧データを紐付ける」ボタンを出す。
- **何回**: メンバー 1 人につき、旧氏名 1 つを 1 回指定する(1 組織内)。旧氏名が複数ある人は複数回(§8-3)。
- 手順:
  1. 管理者がメンバー一覧を開く。画面は `GET /api/orgs/:orgId/legacy-names` で、未付け替えの旧氏名と件数(反省 N・軌跡 M・ロードマップ 0/1)を取得する。
  2. 管理者が行の「旧データを紐付ける」を押し、旧氏名の一覧から選ぶ。画面に「反省 N 件・ロードマップ あり を ◯◯さんに付けます」と確認文を出す(軌跡は現状 0 件のため、件数が 0 より大きいときだけ出す案。§8-12)。
  3. 確定すると `POST /api/orgs/:orgId/legacy-claims`。結果の件数を表示する。
  4. 付け替え済みの旧氏名は、一覧に「◯◯さんに付け替え済み」と出て、「取り消す」ボタンが付く。
- 旧氏名は組織管理者が見て判断する(部内の人間関係で分かる前提)。同姓同名の誤指定は取り消しで戻せる。

## 4. API の形(案・要承認)

認証はいずれもログイン必須・対象組織の組織管理者。メール確認済みを要するかは**既存の組織 API と揃わない**:
`routes/orgs.js` の `gate` は、ログイン(401)・組織の存在(404)・管理者/メンバー(403 `forbidden`)だけを見ており、メール確認済みは見ていない
(確認済みを見るのは招待の参加系と `POST /api/orgs` だけ)。管理者は作成・招待・名簿のいずれの経路でも確認済みのはずなので、
本案は **既存 `gate` をそのまま使い、確認済みの追加検査はしない**ことを推奨する(追加する場合の選択肢は §8-13)。
他組織の管理者(管理者でない人)が `:orgId` を指定した場合は、既存の実装どおり **403 `forbidden`**(404 は組織が存在しないときだけ)。

### 4.1 `GET /api/orgs/:orgId/legacy-names`(案)

- 応答 200: `{ names: [ { legacyName, reflections, sessions, roadmaps, claimedBy: { userId, name, claimId } | null } ] }`
- `names` は、その組織の器に属する `legacy_author_name`・`legacy_owner_name`・`roadmaps.legacy_name` の氏名の和集合。
  件数は「`*_user_id IS NULL`(未付け替え)の行数」。有効な付け替え(§4.2)があれば `claimedBy` を付ける。
- 個人情報の扱い: 旧氏名は組織管理者にだけ返す。メンバー一般には返さない。

### 4.2 `POST /api/orgs/:orgId/legacy-claims`(案)

- 本文: `{ "userId": "u_…", "legacyName": "…" }`
- 処理: ①管理者であること ②`userId` がその組織のメンバーで退会していない ③`legacyName` を trim して空でない
  ④有効な付け替え(`revoked_at IS NULL`)が**別の人**に無いこと(同じ `userId` なら再適用。下記)
  ⑤対象行(所有者 NULL の該当行)の ID を先に選び、`reattachLegacy` と同じ条件でその行を更新する ⑥付け替えた行の ID を記録する(§4.4)。⑤⑥は同一トランザクション。
  `reattachLegacy` 自体は件数しか返さないので、FZ3-I では ID を返す版(または同じ条件で先に SELECT する版)を `accountsRepo` に足す。
- **同じ `userId` への再 POST は再適用**: 有効な付け替えが同じ人に既にあれば、付け替えた後に届いた同じ氏名の行(互換 PUT で増えた反省など)だけを追加で付け、
  項目を既存の記録に足して **200** `{ claim, added: counts }` を返す(冪等。追加 0 件でも 200)。別の人への指定だけ 409。
- 応答 201(新規)/200(再適用): `{ claim: { id, orgId, userId, legacyName, counts: { reflections, sessions, roadmaps }, createdAt } }`
- エラー: 401／403 `forbidden`(その組織の管理者でない。他組織の `:orgId` も同じ)／404(組織なし)／
  422 `invalid_input`(空の氏名・メンバーでない userId・§8-14 で許さない場合の自分自身)／
  **409 `legacy_name_claimed`**(その旧氏名に有効な付け替えが別の人にある)／409 `legacy_nothing_to_claim`(新規で該当データが 0 件。§5.2)。

### 4.3 `POST /api/orgs/:orgId/legacy-claims/:claimId/revoke`(案)

- 本文は任意 `{ "restoreOrgVisibility"?: boolean }`(既定は §8-2 の決定による)。応答 200: `{ ok: true, counts: { reflections, sessions, roadmaps } }`(戻した件数)。
- 既に取り消し済みなら冪等 200。他組織の claimId、または `:orgId` と合わない claimId は 404(招待の revoke と同じ流儀。管理者であることの 403 が先)。

### 4.4 実施記録の表(案・要承認)

```sql
CREATE TABLE legacy_claims (
  id TEXT PRIMARY KEY,            -- lc_…
  org_id TEXT NOT NULL,
  user_id TEXT NOT NULL,          -- 付け替え先
  legacy_name TEXT NOT NULL,      -- trim 済み
  claimed_by_user_id TEXT,        -- 実施した管理者(退会後も残すため NULL 可・FK なし)
  created_at INTEGER NOT NULL,
  revoked_at INTEGER, revoked_by_user_id TEXT
);
-- 有効な付け替えは 1 氏名につき 1 件
CREATE UNIQUE INDEX legacy_claims_active ON legacy_claims(org_id, legacy_name) WHERE revoked_at IS NULL;

-- 付け替えた行の ID。取り消しはこの ID だけを戻す(件数は項目の数から数える)
CREATE TABLE legacy_claim_items (
  claim_id TEXT NOT NULL,
  kind TEXT NOT NULL,             -- reflection | session | roadmap
  row_id TEXT NOT NULL,           -- reflections.id / rec_sessions.id / roadmaps.id
  prev_visibility TEXT,           -- 付け替え時点の公開範囲(反省・軌跡。§8-2 の復元用。不要なら省く)
  PRIMARY KEY (claim_id, kind, row_id)
);
```

- **FK を付けない理由**: `legacy_claims.user_id`・`claimed_by_user_id` は、退会(`users` は匿名化して残るが、将来の物理削除や §8-5 の処理)や管理者の交代後も
  「誰が誰に付けたか」を監査として残すため。既存の `org_members` 等も FK を使っていないので流儀とも合う(要確認:`002_accounts.sql` を FZ3-I で再確認)。
  `legacy_claim_items.row_id` も、互換 PUT が反省を削除しうるため FK なし(取り消しは存在する行だけ戻す)。
- これが監査記録を兼ねる(別の監査表は作らない)。
- 互換 PUT(`dbRepo.syncManagedReflections`)は一致した反省の `legacy_author_name` を `people[0]` で**上書き**する(`author_user_id` と `visibility` は変えない)。
  このため「本人＋氏名」で戻す案だと、氏名が直された行は戻らず、逆に名簿経由で付いた行まで戻してしまう。ID を記録すれば両方の問題が起きない。

### 4.5 設計書 §10.3 に足す文案

> | `GET /api/orgs/:orgId/legacy-names` | 組織管理者 | 未付け替えの旧氏名の一覧 `[{legacyName, reflections, sessions, roadmaps, claimedBy}]` |
> | `POST /api/orgs/:orgId/legacy-claims` | 組織管理者 | `{userId, legacyName}` → 201 `{claim}`。その組織の `legacy_*` のうち所有者が NULL の反省・軌跡・ロードマップを、組織メンバー `userId` に付け替える(§11)。409 `legacy_name_claimed`／`legacy_nothing_to_claim` |
> | `POST /api/orgs/:orgId/legacy-claims/:claimId/revoke` | 組織管理者 | → `{ok:true, counts}`。付け替えを元に戻す(冪等) |
>
> 名簿照合(§4.4)が使えない運用でも、旧データの付け替えは組織管理者が上記で行う。旧氏名は名簿の `legacyName` に依存しない。

**凍結後の既存本文の直し方(案)**:
- §4.4 の「名簿の提出」「照合」「名簿から外れたユーザーは紐付けを解除する」「名簿と違うアドレスで登録したユーザーは紐付かない」の各項目は、
  D3(「組織への紐付けは名簿に含まれる場合だけ」)ごと「v1 では凍結(サーバの処理は残すが Web の入口を出さない)。組織への参加は招待リンクに一本化」と書き換える。
  あわせて `roster_id` が NULL の扱い(作成者・招待参加)の注記は、全員が NULL になるので「名簿凍結中は全員が `roster_id` NULL」に簡略化する。
- §4.4 に 1 項目足す: 「旧データの付け替えは組織管理者が行う(§10.3 `legacy-claims`)。」
- §11 の 716 行目(「部員が登録してメールを確認すると、名簿と照合されて紐付く。そのとき…付け替える。」)は次に置き換える:
  「旧データ(`legacy_*`)の本人への付け替えは、組織管理者がメンバー一覧から旧氏名を指定して行う(§10.3 `legacy-claims`)。
  判断できない軌跡は組織所有のまま残す。名簿を再び使う場合は、名簿の旧氏名による自動付け替えも併用できる。」
- §15 の「名簿照合：…`legacy_*` の付け替え」のテスト項目は、凍結中は名簿を使わない付け替えのテストに差し替える(§7)。

§11 の文案(追記): 「旧データの付け替えは、名簿の旧氏名による自動付け替え、または組織管理者の指定(`legacy-claims`)のどちらでも行える。」

## 5. 取り消し・二重指定・衝突

### 5.1 取り消し

- **取り消しは、記録した行 ID(`legacy_claim_items`)だけを戻す**。「本人＋旧氏名」の一致では戻さない。理由は2つ:
  ①凍結前に名簿経由で付いた同じ氏名の行を巻き込まない ②互換 PUT(`syncManagedReflections`)が `legacy_author_name` を `people[0]` で上書きするため、
  氏名が直された行は氏名一致では見つからない。
  - `reflections`: 項目の ID で `author_user_id = 本人` の行を NULL に戻す。
  - `rec_sessions`: 同様に `owner_user_id`(現状は項目なし)。
  - `roadmaps`: 項目の ID で `user_id = 本人` の行を NULL に戻す。
  - 行が既に削除されている・所有者が変わっている項目は飛ばす(件数に数えない)。
- 本人が新規に作った行は項目に無いので巻き込まない。付け替え後に本人が旧反省を編集した内容は、行ごと NULL 所有に戻るため**内容は残る**(所有だけ戻る)。
- 取り消しは `accountsRepo` に新関数(例 `detachLegacy({claimId})`)で実装する案。取り消し後は同じ氏名を別の人に指定できる。
- **公開範囲の問題**: `policy.canRead` は、`private` で所有者が NULL の反省・軌跡を誰にも読めないとする(所有者でも組織メンバーでも不可)。
  付け替え後に本人が `private` に変えた行を取り消すと、所有者が NULL に戻って**誰にも見えなくなる**(本文は DB に残るが読めない)。
  対応案は ①取り消し時に `private` の行を `org` に戻す(旧データの取込み時の既定が `org` なので元の状態に近い)②戻さずに警告するだけ ③`private` の行があれば取り消しを拒否する。§8-2 で決める。
- 再適用(§4.2)で足した行も同じ項目表に入り、取り消しで一緒に戻る。

### 5.2 二重指定・衝突

| 場面 | 扱い |
|---|---|
| 同じ旧氏名を別の人にも指定 | 409 `legacy_name_claimed`(部分一意インデックスでも守る)。先に取り消してから |
| 同じ旧氏名を同じ人に再指定(付け替え後に同じ氏名の行が増えた) | 200 の再適用(§4.2)。増えた行だけ付け、記録に足す。0 件でも 200。互換 PUT で届いた旧氏名の反省が付かず残る問題をこれで解く |
| 同じ人に別の旧氏名を指定 | 許可を推奨(§8-3)。ただしロードマップは `user_id` UNIQUE のため 2 つ目以降は 0 件になり、応答の `counts.roadmaps` で分かる |
| 本人が既にロードマップを持つ | 反省・軌跡だけ付け替わり、ロードマップは 0 件(既存仕様)。画面で「ロードマップは付け替えられませんでした」と出す |
| 該当が 0 件(氏名の打ち間違い等) | 409 `legacy_nothing_to_claim`、記録は作らない。氏名は一覧から選ぶので通常は起きない |
| 既に所有者のいる行 | 触らない(奪わない)。既存仕様どおり |
| 名簿経路との競合 | 先に付いた方が勝つ。`reattachLegacy` は NULL の行だけ更新するので、後からの名簿照合は上書きしない。名簿経由で付いた分は `legacy_claims` に記録が無く、取り消し対象外(§8-5) |
| 付け替え先が退会 | 設計書 §4.3 は退会で本人の反省・ロードマップを削除する。付け替えた旧データ(元は組織所有の部の記録)まで消えるのは望ましくない恐れがある。現状の `deleteMe` はこの削除をまだ実装しておらず TODO(S3.1 以降)のまま。NULL 所有に戻すか(= 自動の取り消し)は §8-9 で決める。`legacy_claims` の行は FK なしで残す |
| 付け替え後にメンバーが組織から外れる | 所有は残る(「本人のデータは残る」§4.4)。取り消しは管理者が可能 |

## 6. 権限・監査

- 権限は組織管理者のみ。他組織の管理者(その組織の管理者でない人)は既存の `gate` と同じく 403 `forbidden`(404 は組織が無いときだけ。`:claimId` が他組織のものなら 404)。
  管理者でも、対象 `userId` は同組織のメンバーに限る。
- 管理者が自分自身に旧データを付けられるか(自分の旧氏名を自分に指定)は §8-14 で決める。
- 管理者の不正指定(他人の反省を別人に付ける)は、旧データがもともと組織所有で、本人が「自分のもの」と主張する根拠が名簿にしか無かった点を考えると、
  信頼は組織管理者に置く設計になる。対策は ①取り消せる ②`legacy_claims` に実施者・日時が残る ③付け替え先の本人に通知(§8-4)。
- 監査: `legacy_claims` の行(実施者・日時・件数・取り消し)。ログに氏名を出さない(旧氏名は個人情報。ログには claim ID と件数だけ)。
- 回数制限: 管理者の誤操作・連打に備え、書込系(`legacy-claims` の POST と revoke)は本人ごと 1 時間 60 回を推奨する。
  これは組織作成の「本人ごと 1 時間 10 回」(`limiters.orgCreate`)とは**別の値・別の制限器**で、数値は実装値であり利用者決定ではない(§8-8)。

## 7. テスト方針

### 7.1 単体テスト(`test/`、Node 24 の DB テスト)

- `accountsRepo.detachLegacy`(新): 付け替えて戻す往復で元の状態と一致、本人が新規に作った行・他人の行・他組織の行は不変、冪等。
  特に、①名簿経由(記録なし)で付いた同氏名の行は戻さない ②互換 PUT で `legacy_author_name` が書き換わった行も、記録した ID で戻る
  ③`private` に変えた行を取り消したときの扱い(§8-2 の決定どおり)④再適用で増えた行が足され、取り消しで一緒に戻る ⑤付け替え後に削除された行は飛ばす。
- `reattachLegacy`(既存)に、名簿なしの呼び出し(メール・`org_roster` 無し)でも動くテストを追加。
- ドメイン純関数(`server/domain/`): 旧氏名の候補の集計(件数・`claimedBy`)、入力検証(trim・空・長さ)。
- ルート: 管理者 201／非管理者・他組織の管理者 403／組織なし 404／非メンバー userId 422／同一氏名を別の人へ 409／同じ人へ再 POST 200(増えた行だけ)／0 件 409／revoke 冪等・他組織の claimId 404／
  ロードマップが既にある場合の件数 0／トランザクション(記録の挿入に失敗したら付け替えも戻る)。
- 回帰: `linkVerifiedUser`・`applyRoster` の既存テストが無変更で通る。互換 PUT と反省の upsert で軌跡を消さない既存テストが通る。

### 7.2 ハブ e2e(`scripts/e2e-sailviz.mjs`)

- 一時データに、`people[0]` が旧氏名(架空名)の反省を持つ旧形式プロジェクトを用意し、旧データの取込み(旧形式プロジェクトの PUT)で `legacy_author_name` を作る。
  (要確認:現在の e2e がこの種の旧データを作れるか。作れなければシナリオ側で旧 API の PUT を足す)
- 流れ: 管理者と一般メンバーを登録・確認 → 招待で一般メンバーが参加 → 管理者が `legacy-names` を取得(件数あり)→ `legacy-claims` で付け替え(201・件数)
  → 本人の `GET /api/practice-days` 等で自分の反省として見える → 二重指定 409 → revoke → 元に戻る → 再度別のメンバーに付け替えられる。
- 画面(1280px・390px): メンバー一覧に「旧データを紐付ける」が出ること。変更前の版では FAIL、変更後で PASS になるように書く(FZ3-I で実施)。
