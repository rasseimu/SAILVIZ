# sailviz サーバ移行計画 — 現行（ファイル保存＋共有ログイン）から v2（SQLite＋アカウント＋記録セッション＋声の反省）へ

- **日付**: 2026-10-04（改訂3）
- **前提資料**: ①現行サーバ設計メモ（server/ の構成・認証フロー・データスキーマ） ②設計書 v2 改訂4（`2026-10-04-sailviz-field-design-v2.md`）
- **役割分担**: データモデルと API は**設計書 v2 を正**とする。本書は「どの順で、どう安全に置き換えるか」を決める
- **配置先（想定）**: `docs/superpowers/specs/2026-10-04-sailviz-server-migration-plan.md`

| 改訂 | 内容 |
|---|---|
| 改訂1（2026-10-04） | 初版（5段階） |
| 改訂2（2026-10-04） | SQLite と練習の器（組織×日付）を確定。ミーティング（録音 → 議事録 → 反省の自動送信）の段階を追加し、8段階に。スキーマは設計書 v2 §5.1 に一本化 |
| 改訂3（2026-10-04） | Phase 5 を「声の反省と練習日の議事録」に変更（各自が自分のスマホに話す方式） |

## 0. 結論

- **8段階で置き換える**：土台 → 保存先を SQLite へ → アカウント → 記録セッション（主機能）→ アプリ向け API → 声の反省と議事録 → Web の移行 → 旧経路の撤去。どの段階も単独で本番に出せて、1つ前に戻せるようにする。
- **最初の鍵は「リポジトリ層」**：`storage.js` を直接呼んでいる API の手前に保存の窓口を1枚挟み、保存先（ファイル／DB）を API から切り離す。Web の見た目を変えずに中身だけ移せる。
- **DB は SQLite（`node:sqlite`）に決定**。依存ゼロ・Fly 1台・/data ボリュームの方針をそのまま保つ。
- **練習の器は現行どおり「組織×日付」**。公開範囲は軌跡と反省ごとに作成者が設定する（設計書 v2 改訂3 に反映済み）。

```
P0 土台 → P1 SQLiteへ → P2 アカウント → P3 記録セッション → P4 アプリ向けAPI → P5 声の反省・議事録 → P6 Web移行 → P7 撤去
(挙動不変)  (見た目不変)   (共有ログインと並走)  (主機能:乗員・艇番・CSV)  (反省・進捗・ロードマップ)  (話す→自分の反省へ)  (旧API呼び出しゼロへ)

アプリ開発: P0 と並行で開始（サーバ不要な部分から）→ P3 からステージングに接続 → P5 で声の反省を接続
```

## 1. 現状の要点（移行に効くところ）

| 項目 | 現状 | 移行への影響 |
|---|---|---|
| ランタイム | Node 20 | Node 20 は 2026-04-30 でサポート終了済み。最初に更新する |
| 依存 | Node 標準のみ（フレームワーク・DB なし） | 維持する。DB は `node:sqlite`、ハッシュは `crypto.scrypt`、トークンは `crypto.randomBytes`、SHA-256 は `crypto.createHash`、外部 API（メール・Gemini）は標準の `fetch` |
| デプロイ | Fly.io nrt・1台・`/data` ボリューム・`auto_stop_machines` | SQLite と相性が良い。ボリュームはマシンごとなので**マシンは1台のまま**。休止でバックグラウンド処理が止まりうる点は声の反省の処理で考慮する（P5） |
| 保存の単位 | 1練習＝1ファイル（複数艇の軌跡・複数人の反省）。last-write-wins | 「練習日の器（組織×日付）」として DB でも残す |
| 軌跡 | `tracks[].points` をプロジェクトに埋め込み。`source.importId` で取込と対応 | 表に分ける。`imp_…` をセッション ID としてそのまま使う |
| 人のキー | 反省は `people[0]`、ロードマップは人名がキー | 移行時は人名を `legacy_*` として持ち、名簿照合で userId に付け替える |
| progress.json | 反省ID ごとの課題ステージ・目標達成・指導コメント | 進捗とコメントの表に移す |
| 議事録取込 | 複数人の反省を一括で作る（`minutesimport.js`） | 残す。声の反省と「反省への反映ルール」を共通化する |
| AI | `gemini.js`（キーはサーバ）、`/api/ai-comment` | 声の反省の文字起こし・整理と、練習日の議事録づくりにも使う |
| 認証 | 共有の閲覧ゲート（既定値がコードに入っている）＋書き込みトークン。閲覧ログイン＝書き込み可 | 既定値の埋め込みは最初に外す。アカウント導入後は所有者と公開範囲で認可する |
| セッション | 起動時に作る秘密値を Cookie と照合。再起動で全員失効 | 休止から起動するたびに全員のログインが切れているはず（要確認）。DB に保存するトークンで解消する |
| Bearer | `extractToken` が `Authorization: Bearer` に対応済み | アプリの Bearer 認証はこの仕組みを広げて使う |
| 地理院タイルプロキシ | 認証不要 | そのまま |
| テスト | storage は `dataDir` 注入、auth は純関数 | 同じやり方でリポジトリ層・認可判定・変換を作る |

## 3. 段階的な移行

各段階は「ステージングで確認 → 本番」の順に出す。データモデルと API の詳細は設計書 v2 の該当節を参照。

### Phase 0：土台づくり（挙動は変えない）
**やること**
- 現状調査レポート：ルーティング、テスト、`fly.toml`、`sensorimport.js` と `minutesimport.js` の入出力、実データの形（同じ日付のファイルが複数あるか、`sensorLogs`・`tracks`・`videos` の形）、Web の保存処理。
- Node 20 → 24 LTS（Docker のベースイメージ）。既存テストを全部通す。Node 26 が LTS に入ったら、`node:sqlite` の安定度を見て上げる。
- **ステージング環境**：別の Fly アプリ（例 `sailviz-staging`）に本番 `/data` のコピーを置く。以後の全段階をここで先に試し、アプリ開発の接続先にも使う。
- 共有ゲートの既定値をコードから外し、環境変数を必須にする。
- `api.js` を `routes/` に分割する（エンドポイントは変えない）。
- `storage.js` の呼び出しを、リポジトリ層の経由に変える（中身はファイルのまま）。
- 本番 `/data` を丸ごとバックアップし、Fly のボリュームスナップショットの保持設定を確認する。マシンが1台であることを確認する。

**完了条件**：既存テストがすべて通り、本番の動きに差がない。
**戻し方**：前のイメージに戻す。

### Phase 1：保存先を SQLite に差し替える（見た目は同じ）
**やること**
- `node:sqlite` で `/data/sailviz.db` を作る（WAL）。マイグレーションの仕組みを入れる。
- 設計書 v2 §5.1 の「練習・記録・反省」の表を作る（アカウント関係はまだ）。
- 純関数 `decomposeProject`（旧 JSON → 行）と `assembleProject`（行 → 旧 JSON）。表に対応しないキーは `extra` に入れて捨てない。
- 取込スクリプト（ファイル → DB）。`--dry-run` で件数と警告（対応する反省がない progress のキーなど）を出す。2回流しても結果が同じ。
- **往復テスト**：本番データのコピー全件で「ファイル → DB → 旧 JSON」が元と一致する（配列の順序・欠けているキーを含む）。
- DB 版のリポジトリを実装し、`STORAGE=file|db` で切り替えられるようにする。既存 API はすべて DB 版で動かす。
- `PUT /api/projects/:name` は削除ルール付きで行に分けて書く（設計書 v2 §10.8。組み立てた JSON に `_rev` を付ける）。
- **書き戻しスクリプト**（DB → ファイル）を用意する。これが戻し道になる。
- ステージングで一定期間使ってから本番を切り替える。旧ファイルは読み取り専用で保管する。

**完了条件**：Web の全機能（練習を開く、反省・進捗・コメント・ロードマップ、CSV 取込、議事録取込、AI コメント）が DB 版で同じように動き、往復テストが全件一致する。
**戻し方**：書き戻しスクリプト → `STORAGE=file`。

### Phase 2：アカウントと名簿（共有ログインと並走）
**やること**
- アカウント・組織の表を追加する（設計書 v2 §5.1）。
- 登録・メール確認・ログイン・再設定・削除（§10.2）。パスワードは scrypt、トークンは DB にハッシュで保存する。**再起動や休止でログインが切れなくなる**。
- メール送信は外部サービスの HTTP API を `fetch` で呼ぶ（サービスは要選定）。
- 認可を `policy.js` に集める（設計書 v2 §5.8）。
- **旧共有ログインは「芝浦の組織メンバー（書き込み可）」として扱い、並走させる**。部員は自分のペースで登録できる。
- 名簿：組織管理者が Web で提出 → 確認済みメールで照合 → 名簿の「旧名簿の氏名」と一致する `legacy_*` のデータ（反省の作者、ロードマップ、判断できる軌跡の所有者）を本人に付け替える。残りは組織所有。
- Web にアカウントのログイン画面と名簿画面を追加する。

**完了条件**：部員が自分のアカウントで使え、旧データが本人に紐付いている。
**戻し方**：アカウント経路を閉じる（共有ログインは並走中なのでそのまま使える）。

### Phase 3：記録セッション API（アプリの主機能）
**やること**
- 記録セッション・乗員・チャンクの API（設計書 v2 §7・§10.4）とレース記録の表。
- finalize は `sensorimport.js` のパースとトラック構築をそのまま使う。`csv_name` は既存 commit のリネーム規則。
- 紐付け先：練習は練習日の器（組織×日付／本人×日付）、レースはレース記録。
- Web の CSV 取込（`sensor-imports → commit`）を同じ流れの上に作り直す（旧エンドポイントは薄い包み）。
- `GET /api/sessions/:id/csv` と `/track`。旧データの CSV（`uploads/<importId>/*.csv`）を seq 0 の1チャンクとして取り込む。

**完了条件**：ステージングで、アプリ（または同じ手順の検証スクリプト）から送った記録が、Web の練習日に艇として表示され、CSV をダウンロードできる。チャンクの再送・欠番・二重 finalize のテストが通る。Web の古い画面からの保存で、新しく届いた軌跡が消えない。
**戻し方**：新エンドポイントを閉じる。Web の CSV 取込はフラグで旧経路に戻せるようにしておく。

**ここで初めてアプリの本番配布ができる**（GPS の記録とアップロード）。

### Phase 4：アプリ向け API
**やること**
- `/api/practice-days`、`/api/me/reflections`（公開範囲を含む）、`/api/reflections/:id/progress`・`/comments`、`/api/me/roadmap`、`/api/race-records`、`/api/orgs/:orgId/members`（設計書 v2 §10.3・§10.5・§10.6）。

**完了条件**：アプリから反省・ロードマップ・ホームの表示・履歴が動く。互換 API 経由の Web と、新 API 経由のアプリで、同じ反省が同じ内容に見える。
**戻し方**：新エンドポイントを閉じる。

### Phase 5：声の反省と練習日の議事録
**やること**
- 声の反省・練習日の議事録・ジョブ・用語集の表（設計書 v2 §5.1）。音声はボリューム上のファイル（`/data/audio/<voiceId>/`）。
- 音声チャンクの受信と finalize（設計書 v2 §10.7）。
- **ジョブワーカー**：`jobs` から順に処理し、サーバ起動時に未完了のものを再開する。段階は文字起こし → 整理 → 反映。
- **Gemini**：音声を直接入力して文字起こし（本人の氏名・艇番・用語集を手がかりに渡す）→ 文字起こしを反省の項目に整理した JSON（§9.5）。扱える音声の長さ・形式・料金を実装前に公式ドキュメントで確認する。
- **`applyToReflection`（純関数）**：反映のルール（§9.6）と取り消し。Web の議事録取込（`minutesimport.js`）も同じ関数を通す。
- **練習日の議事録**：組織メンバーのボタンでジョブを登録し、所属内以上の反省だけを材料に作る（§9.8）。
- 用語集の API と Web 画面。初期値として芝浦の誤変換リストを入れる。
- 音声の 30 日削除（ジョブ）、1ユーザー1日の処理回数の上限。
- **Fly の休止への対策**：処理中にマシンが止まっても、次のアクセスで再開する。アプリは処理中に状態を数秒〜数十秒おきに取りに行く。

**完了条件**：ステージングで、ミーティングの場で録音した声の反省が本人の反省に入る。既にある内容を上書きしない、取り消しで元に戻る、処理の途中で再起動しても完了する、議事録に「自分のみ」の反省が入らない、をテストで確認する。
**戻し方**：声の反省と議事録の API・ワーカーを止める（他の機能に影響しない）。

### Phase 6：Web の移行
**やること**
- Web フロントを新 API に順に切り替える（`/api/projects` → `/api/practice-days`・`/api/sessions`、overlays → 進捗・ロードマップ API、議事録取込 → 共通変換）。
- 公開範囲の設定 UI、議事録の閲覧画面、用語集の管理画面。
- 部員の登録がそろったら、共有ログインと書き込みトークン（`/api/login`・`/api/unlock` 系）を止める。

**完了条件**：Web が旧 API を呼ばなくなる（アクセスログで確認）。共有ログインが停止している。
**戻し方**：Web を前のバージョンに戻す（旧 API は Phase 7 まで残っている）。

### Phase 7：撤去
- 旧 API（`/api/projects`、`/api/summaries`、`/api/overlays`、`/api/sensor-imports`、`/api/minutes-imports` の旧形式、`/api/uploads`、`/api/session`、`/api/login`、`/api/logout`、`/api/unlock`、`/api/lock`、`/api/auth`）を削除する。
- ファイル版のリポジトリと `storage.js` を削除する。旧ファイルはアーカイブとして保管する。

### アプリ開発との並行

| アプリの作業 | 接続できるサーバの段階 |
|---|---|
| 記録・ローカル保存・チャンク封入・録音・純関数・権限 | サーバ不要（P0 と並行） |
| ログイン・GPS の自動アップロード（主機能） | P3（ステージング）→ P3 本番反映後に配布 |
| 反省・ロードマップ・ホーム・履歴 | P4 |
| 声の反省・練習日の議事録 | P5 |

## 4. 旧データとの対応

表の定義は設計書 v2 §5.1 を正とする。

| 旧 | 新 |
|---|---|
| `projects/<name>.sailviz.json` | `practice_days`（`legacy_name`＝ファイル名、`web_state`、組織所有） |
| `tracks[]` | `rec_sessions`（`id`＝`imp_…`、`source`、公開範囲 `org`）＋ `tracks`（点列・表示設定） |
| `sensorLogs[]` | `rec_sessions.source` から組み立てる |
| `reflections[]` | `reflections`（`legacy_author_name`＝`people[0]`、公開範囲 `org`） |
| `progress.json` | `reflection_progress` ＋ `reflection_comments` |
| `roadmap.json` | `roadmaps`（`legacy_name`＝人名キー） |
| `uploads/<importId>/*.csv` | `chunks`（seq 0）と `tracks.csv_name` |

- 同じ日付の旧ファイルが複数ある場合は、別の器のまま移す。新しい項目はその日に最初に作られた器に入れる。統合するかは後で判断する。

## 5. 互換 API と認可の扱い

- 互換 API の仕様と削除ルールは設計書 v2 §10.8。認可の表は §5.8。
- **Phase 1 の間**は認可を現行どおりにする（共有ログインで全部読める・書ける）。Phase 2 から `policy.js` の判定に切り替え、旧共有ログインは「芝浦の組織メンバー」として扱う。
- Web が未知のキー（`_rev`）を保持したまま送り返すかは Phase 0 で調べる。保持しない場合は、Web 側で `_rev` を送り返す小さな対応を入れる。それまでは「`_rev` の無い PUT ではトラックを削除しない」ルールで守る。

## 6. テストと検証
- **往復テスト**：本番データのコピー全件で、ファイル → DB → 旧 JSON が一致する。差分はレポートに出す。
- **既存テスト**：全段階で通す。
- **取込スクリプトの冪等性**：2回流しても行数と内容が変わらない。
- **削除ルール**：古い `_rev` の PUT で、新しく届いた軌跡が消えない。
- **認可の表テスト**（設計書 v2 §5.8）。
- **声の反省と議事録**：`applyToReflection` の各ルール、議事録の材料の絞り込み、ジョブの再開、Gemini を偽物に差し替えた固定応答での通し。
