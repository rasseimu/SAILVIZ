# 風速帯別 AIコメント高度化 設計

作成日: 2026-09-23

## 目的と背景

セーリングでは風速によって有効な技術が大きく変わる。現状の AIコメント生成は
2系統(参考文献ベース `aicomment.js` / ピア学習ベース `peerlearning.js`)あるが、
風速をコメントの一級の判断材料として扱えていない。`aicomment.js` は風速を全く
使わず、`peerlearning.js` は evidence 並べ替えの副次キーとして使うだけである。

本設計では次の2点を実現する。

1. **反省(目標・課題・発見・遅い/速い要因)を風速帯に結びつける。** 数値風速だけで
   なく、文中の風速表現語(微風/中風/順風/強風/爆風)を優先的に使って分類する。
2. **風速帯×課題×有効技術の相関を事前に一度だけ分析し、Markdown ダイジェストとして
   キャッシュする。** 各コメント生成時はこのダイジェストの該当風速帯セクションだけを
   注入することで、毎回の分析を避けつつ(トークン節約)、質の高い助言を安定して出す。

## 設計判断(確定事項)

| 項目 | 決定 |
|------|------|
| ダイジェストの中身 | チーム反省データのAI分析(相関マイニング)。参考文献はデータ希薄な帯の補完に使う |
| 風速帯 | 4帯。微風 <3 / 中風・順風 3〜6 / 強風 6〜10 / 爆風 10+ m/s |
| 語 vs 数値 | 文中の風速表現語が数値に優先。数値は語が無いときのフォールバック |
| 生成方式 | フルAI分析(1回のGemini呼び出し)。JSで入力を組み立てAIが相関を執筆 |
| 保存・更新 | localStorage にキャッシュ。手動「再構築」ボタン。閲覧・.mdダウンロード可 |
| 消費先 | 既存2系統(aicomment / peerlearning)を両方とも風速帯対応に拡張。新種別は追加しない |
| 帯マッチング | 同帯優先フィルタ + 不足時は隣接帯へ拡大(filter-with-fallback) |
| バンドモデル統合 | Approach A: 既存3ビン `WIND_BINS` を4帯 `WIND_BANDS` に置換(表示グリッドも4列化) |

## アーキテクチャ概観

```
                 反省(localStorage) + progress overlay
                              │
        ┌─────────────────────┴───────────────────────┐
        │  windband.js  (バンドモデル・語解析・帯フィルタ) │
        └─────────────────────┬───────────────────────┘
                              │ classifyWindBand / filterByBand
   ┌──────────────────────────┼──────────────────────────────┐
   │                          │                              │
progressstore.summarize   windknowledge.js              aicomment.js /
(発見の帯別グリッド)      (相関ダイジェスト構築)          peerlearning.js
                              │  1回のGemini分析              │ 該当帯セクション注入
                              ▼                              │ + 帯フィルタ(fallback)
                   windknowledgestore.js                     ▼
                   (localStorage キャッシュ)          コメント生成(2系統)
                              │
                        再構築ボタン / 表示・DL
```

## コンポーネント設計

### 1. `src/windband.js` — バンドモデル・語解析・帯フィルタ(新規)

単一の風速語彙をアプリ全体で共有する。純ロジックのみ。

```js
export const WIND_BANDS = [
  { key: 'bihuu', label: '微風 (〜3 m/s)',      max: 3,        words: ['微風', '無風'] },
  { key: 'chuu',  label: '中風・順風 (3〜6 m/s)', max: 6,        words: ['中風', '順風'] },
  { key: 'kyou',  label: '強風 (6〜10 m/s)',     max: 10,       words: ['強風'] },
  { key: 'baku',  label: '爆風 (10 m/s〜)',      max: Infinity, words: ['爆風'] },
];
```

**`classifyWindBand(text, speed)`**
1. **語優先。** `text` を各帯の `words` で走査。見つかればその帯。複数帯の語が同時に
   出現した場合は最も強い帯(配列で後ろ=強風側)を採用する。
2. **数値フォールバック。** 語が無く `speed` が有限なら `max` 未満の最初の帯。
   境界は現行 `windBinKey` と同じく `< max`(排他)。
3. どちらも無ければ `'unknown'`。

`text` の供給元: 特定フィールドを分類する際はそのフィールドのノート文を先に走査し、
無ければ反省全体のノートへフォールバックする。`無風` は微風の同義語として畳み込む。
語の拡張(そよ風・ブロー等)は `words` 配列の1箇所で行う。

**`filterByBand(candidates, targetBand, { min = 2, getBand })`**
- 同帯候補が `min` 以上 → 同帯のみ返す。
- 不足 → 隣接帯(配列の前後)へ拡大。
- なお不足 → 全候補。
- `getBand(candidate)` が `'general'`(帯非依存)を返す候補は常に対象に含める。

**`bandSectionFromDigest(bandBullets, bandKey)`**
- 指定帯の bullet 配列を返す。未構築/欠損帯は空配列。

### 2. `src/windknowledge.js` — 相関ダイジェスト構築(新規)

純ロジック(入力組み立て・プロンプト・応答検証)を API 呼び出しから分離。

**入力A: チームデータバンドル(主)** — 全反省 + progress overlay を走査。各フィールド
(goal/issue/discovery/slowFactor/fastFactor)を `classifyWindBand` で帯付けし、帯ごとに:
- 解決済み課題(stage 2)・達成済み目標(done)と、同一部員がその後に書いた発見/変化
  (既存 `buildHistoryPool` の形を再利用);
- 単独の発見・遅い/速い要因。
部員実名は除去する(このダイジェストは「技術」層。実名引用は peerlearning の役割)。

**入力B: 参考文献(補完)** — `src/references` 各ソースの `summary` を、タイトル+要約への
語走査(`classifyWindBand` 再利用)で帯タグ付け。風速語を含まないソースは共有の
`general` プールとしてどの帯でも利用可能にする。参考文献は全帯をカバーするため、
データ希薄な帯でも「データ不足」で空にならない。

**AI分析パス(再構築時のみ、1回)** — システムプロンプト要旨:

> あなたは経験豊富なセーリングコーチです。以下はチームの解決済み課題・それを解決した
> 発見・単独の気づきを風速帯別にまとめたものです。各帯について、繰り返し現れる
> 「課題→有効な技術」の相関を簡潔な箇条書きで書いてください。同義の言い回しは1点に
> クラスタします(例: カニンガムを緩める / 緩めて走らせる → 1点)。部内実績を優先し、
> データが少ない帯は参考文献で補完・裏付けします。各帯 最大8点。データ・資料にない
> 内容は憶測で書かない。

出力は帯キー別の JSON。各 bullet に軽量な出典タグを持たせる:
- `〔部内実績〕` = チームデータ由来
- `〔参考: <title>〕` = 参考文献由来

**出力アーティファクト(Markdown)** 例:

```md
# 風速帯別 課題×有効技術 相関ノート  (更新: 2026-09-23)

## 微風 (〜3 m/s)
- 「走らない/艇速が出ない」→ カニンガム/アウトホールを緩めセールを深く 〔部内実績〕
- 「頭が落ちる」→ … 〔参考: 微風のランニング〕

## 中風・順風 (3〜6 m/s)
- …

## 強風 (6〜10 m/s)
- …

## 爆風 (10 m/s〜)
- ベアアウェイ時はベン下を大きく引きオーバーヒール前にメインを逃がす 〔参考: 強風のクローズのコツ〕
- ラダー操作は最小限、艇を立てて走らせる 〔部内実績〕
```

**応答検証** — 帯別 JSON を検証し、8点/帯の上限を強制、欠損帯を許容、不正出力は例外
(`parseGroundObject`/`parseScreen` と同様の作法)。

### 3. `src/windknowledgestore.js` — キャッシュ(新規)

`progressstore.js` の作法に倣った load/save/clear。localStorage キー
`sailviz.windknowledge`:

```js
{
  md: string,                 // レンダリング済みドキュメント(表示・DL用)
  builtAt: number,            // 構築時刻(ms)
  bandBullets: {              // マークダウン再パース不要の帯別配列
    bihuu: [...], chuu: [...], kyou: [...], baku: [...]
  },
  stats: { reflections, resolved, perBand }  // トースト・鮮度表示用
}
```

破損 localStorage は空扱い(`loadProgress` と同様)。

### 4. 既存2系統の拡張

両系統を風速帯対応にする。共通機構:

**対象帯の算出** — コメント対象の反省フィールドごとに
`classifyWindBand(fieldText, speed)` で帯を求める。

**ダイジェスト注入** — キャッシュから **対象帯のセクションだけ**(≤8点)を取り出し、
根拠付け(grounding)プロンプトに追加コンテキストとして注入:

```
# 風速帯の技術ノート({帯ラベル})
{その帯の箇条書き}
```

grounding システムプロンプトに1行追加: 「上の技術ノートも判断材料にしてよい
(該当すれば引用する)。憶測はしない。」 スクリーニングプロンプトは変更しない
(安価に保つ)。常に1帯分のみ送るため、1コメントあたりのトークン増は小さい。

**帯マッチング(filter-with-fallback)** — スクリーニングの候補集合に適用:
- `peerlearning.js`: `buildHistoryPool` は既に各プール項目に帯を付与。新ステップとして
  プールを対象帯にフィルタし、`min`(=2)未満なら隣接帯→全体へ拡大。現行の
  並べ替えのみのタイブレークを prefer-then-widen に置換。
- `aicomment.js`: 参考文献ソースを帯タグ付け(builder と同じ走査)。スクリーニング
  候補を対象帯+general に絞り、不足時は隣接帯へ拡大。general(帯非依存)は常に対象。

**配線** — 共通ヘルパー(`windband.js`)が `classifyWindBand` /
`bandSectionFromDigest` / `filterByBand` を公開し、両系統から使う。fallback ロジックは
1箇所に集約する。

**ダイジェスト不在時の degrade** — キャッシュ未構築(localStorage 空)なら、注入
ブロックを省き帯フィルタは現行動作(並べ替えのみ)に劣化する。初回再構築前でも
コメントは動く。

### 5. UI

**再構築ボタン** — 進捗/練習ページのツールバー、既存 AIコメント操作の隣に
「風速帯ノートを再構築」。クリックで:
1. チームバンドル + 帯タグ付き参考文献要約を JS で組み立て、
2. 既存 `/api/ai-comment` プロキシ経由で Gemini を1回呼び、
3. パースして localStorage に保存、
4. トースト「更新しました(微風X・中風Y・強風Z・爆風W 件)」。
実行中はスピナーで無効化。失敗はエラートーストを出し、以前のダイジェストを保持する。
ここが知識ベースのためにトークンを使う唯一の場所。

**表示 / ダウンロード** — 「ノートを表示」で `md` を読み取り専用パネル/モーダルに表示。
**.md ダウンロード** ボタンと `builtAt` タイムスタンプ・鮮度ヒント
(「最終更新: 9/23 ・ 反省N件」)を付ける。localStorage に住むが随時実ファイルとして
書き出せる。

**認証** — 再構築は他の AIコメント操作と同じ閲覧ログイン/書き込み権限を要求
(`server/api.js` の既存チェック)。

## データフロー

**再構築(手動・低頻度):**
反省+progress → windband 帯付け → windknowledge 入力組み立て(チーム+参考文献)
→ Gemini 1回 → 検証・レンダリング → windknowledgestore 保存 → トースト。

**コメント生成(高頻度・毎回):**
対象反省 → classifyWindBand → 候補を filterByBand(fallback) → スクリーニング →
根拠付けに該当帯セクション注入 → コメント(既存フォーマット、出典付き)。

## エラーハンドリング

既存の「1件の失敗で全体を止めない」方針を踏襲:
- 再構築の AI 呼び出し失敗 → 以前のダイジェスト保持 + エラートースト。
- AI 応答が不正 → パーサが例外 → ボタンハンドラで捕捉。
- 個々のコメント生成失敗は従来どおり個別に握りつぶす。
- ダイジェスト未構築は通常の no-op(エラーではない)。
- localStorage 破損 → 空扱い。

## テスト方針(Node built-in test runner)

**`windband.js`**
- `classifyWindBand`: 語が数値に優先(`爆風で走らない`+speed4→`baku`);数値フォール
  バックの各境界(2.9→微風, 3→中風, 6→強風, 10→爆風, `max`排他);`無風`→微風;
  複数帯の語→最強帯;語なし+speed null→`unknown`。
- `filterByBand`: 同帯が min 以上なら同帯のみ;不足で隣接拡大;なお不足で全体;
  general は常に対象。
- `bandSectionFromDigest`: 正しい帯の bullet を返す;欠損帯は空配列。

**`windknowledge.js`**
- チームバンドル組み立てが解決課題→後続発見を帯別に正しくまとめ、実名を除去する
  (既存 `buildHistoryPool` テストを拡張)。
- 参考文献の帯タグ付け: タイトル/要約の語走査が正しく分類;語なしは `general`。
- プロンプト builder が両入力と「≤8点/帯・憶測禁止」指示を含む。
- 応答パーサ: 帯別 JSON を検証、8点上限を強制、欠損帯を許容、不正出力を拒否。

**生成拡張(`aicomment.js` / `peerlearning.js`)**
- スクリーニング候補が帯フィルタ+fallback される。
- 根拠付けプロンプトに注入帯ノートが含まれる。
- **ダイジェスト不在パス**が現行動作に劣化する(回帰ガード)。

**`windknowledgestore.js`**
- load/save/clear ラウンドトリップ;破損 localStorage → 空扱い。

## 影響範囲・移行

- `progressstore.js`: `WIND_BINS`(3)→`WIND_BANDS`(4)にリネーム置換。`summarize()` は
  `classifyWindBand(text, speed)` を使い、発見の帯別グリッドは4列化。既存テスト更新。
- `peerlearning.js`: `windBinKey` 依存を `classifyWindBand` へ、evidence 並べ替えを
  `filterByBand` ベースへ。
- 表示グリッドの4列化に伴う CSS/レイアウト微調整。
- 既存 localStorage データは無変更(overlay 別ストア)。ダイジェストは初回ボタンで生成。

## 非目標(YAGNI)

- ダイジェストの自動再構築(手動ボタンのみ)。
- サーバー側保存・チーム間同期(localStorage のみ)。
- 参考文献 PDF 全文の分析パスへの投入(要約のみ使用)。
- 風速帯以外の相関軸(波高・リグ設定等)。将来の別設計とする。
