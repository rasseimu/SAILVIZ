# 組織の切り替えとアカウントでの書き込み 設計書

- 日付: 2026-10-22
- ベース: `origin/develop`(7eb6e40)
- 関連: 移行計画 `docs/2026-10-04-sailviz-server-migration-plan.md`(Phase 6 の一部を前倒し)、権限の正本 `server/domain/policy.js`(設計書 v2 §5.8)

## 1. なぜ作るか

staging(`sailviz-sit-staging`、`STORAGE=db`)で、アカウントでログインした部員が全体目標を保存すると `同期に失敗 (403)` になる。今の Web は保存をすべて旧 API(`/api/projects`・`/api/overlays/*` など)で行っており、旧 API で書けるのは共有の書き込みトークンだけ(`server/routes/compat.js` の `gateWrite` → `isCompatWriter`)だからである。

一方、アカウントでは 1 人が複数の組織に入れる。全体目標は組織ごとのものなので、どの組織の目標を見て書くのかを、利用者が選べる必要がある。

利用者の言葉で:

- 「全体目標は組織に依存する。二つ組織に入っているのなら、選択し、それぞれ書けるようにしなければならない。」
- 「全体目標はそんなにかえるものじゃない。組織に複数入っている人は組織管理で組織のボタンをクリックして表示する組織を切り替えるようにしよう。」

## 2. 目標

1. **表示中の組織を選べる。** 複数の組織に入っている人は、組織管理の画面(`/account#org`)で組織のボタンを押し、表示する組織を切り替えられる。
2. **表示が組織ごとに切り替わる。** 表示中の組織を切り替えると、ホームの「全体目標」と「練習一覧」がその組織のものだけになる。練習を開いたときの中身、進捗・コメント、ロードマップも、その組織のものだけになる。
3. **アカウントで書ける。** アカウントでログインした組織メンバーは、表示中の組織の練習・反省・進捗・コメント・全体目標・ロードマップを、誰が作ったものでも書き換えられる(作成者に限らない)。練習の削除もできる。
4. **新しく作ったものは表示中の組織に入る。** アカウントで新規に保存した練習・反省・ロードマップの行は、表示中の組織に属する。
5. **全体目標は組織ごとに 1 件。** 今はサーバー全体で 1 件(roadmap オーバーレイの予約キー `__team__`)。これを組織ごとに 1 件にする。

## 3. 目標にしないこと

- 新 API(`/api/practice-days`・`/api/sessions` など)への Web の全面移行(Phase 6 の本体)。今回は旧 API を使ったまま、アカウントで書けるようにする。
- 共有ログイン・書き込みトークンの廃止。今までどおり使える。
- 公開範囲(private / org / public)を設定する UI。
- 組織をまたいだ表示(全組織の練習を混ぜて見る)。
- 組織の削除・組織間のデータ移動の UI。

## 4. やってはいけないこと(動いても失敗とみなすもの)

- 別の組織のデータが、表示中の組織の画面に混ざる。書き換えられる。消える。
- 書き込みトークンで使っている人の今の使い方(`MIGRATION_ORG_ID` の組織を読み書き)が壊れる。
- 組織 A の全体目標を保存したら、組織 B の全体目標が消える・上書きされる。ロードマップの人名の行も同じ。
- 進捗 PUT(全置き換え)で、表示中でない組織の反省の進捗が消える。
- 1 つの組織にしか入っていない人の操作が増える(切り替えボタンが出る、毎回選ばされるなど)。

## 5. 決まっていること

### 5.1 表示中の組織の選び方(Web)

- 組織管理の画面(`src/account/main.js` の組織の画面)に、所属する組織ごとのボタンを並べる。押した組織が「表示中の組織」になる。
- 所属が 1 つだけの人には、切り替えボタンを出さない。
- 選んだ組織はブラウザに覚えさせる(`localStorage`)。次に開いたときも同じ組織を表示する。
- 覚えている組織が無い、または今は所属していない場合は、`/api/me` の `orgs[0]` を使う。
- 切り替えは表示だけの選択で、データの所属・権限は変わらない。

### 5.2 サーバーに表示中の組織を伝える

- Web は、API への全リクエストに表示中の組織の ID をヘッダー **`X-Sailviz-Org: <組織ID>`** で付ける。sailviz-field(Flutter アプリ)も同じヘッダーを使うので、名前は固定。
- サーバーは、旧 API だけでなく、今後作る新 API(`/api/practice-days`・`/api/me/reflections` など、設計書 v2 の API)でも、組織で絞る処理にはこのヘッダーを使う(§5.10)。
- サーバーは、アカウントでログインした主体(`user`)について、その ID が本人の所属組織か確かめる。所属していなければ 403。
- ヘッダーが無いときは、所属組織の先頭(`/api/me` の `orgs[0]` と同じ順)を表示中の組織とみなす。
- 共有の書き込みトークン・閲覧ゲートの主体(`legacy`)は、ヘッダーを無視する。今までどおり `MIGRATION_ORG_ID` の組織に限る。

### 5.3 読み取りを表示中の組織に絞る

アカウントの主体では、旧 API の読み取りを表示中の組織に限る。

- `GET /api/projects`・`GET /api/summaries`: 器の組織(`practice_days.org_id`)が表示中の組織のものだけ。
- `GET /api/projects/:name`: 器が表示中の組織でなければ 404。
- `GET /api/overlays/roadmap`: 表示中の組織の行だけ。全体目標(`__team__`)は表示中の組織の 1 件。
- `GET /api/overlays/progress`: 表示中の組織の練習にある反省の進捗だけ。

他組織の public な練習も、表示中の組織でなければ出さない。

### 5.4 書き込みの権限

利用者の決定: **アカウントでログインした組織メンバーは、その組織の練習・反省・進捗・コメント・全体目標・ロードマップを、作成者に関係なく書き換えられる。**

- 今の `policy.js` の `canWrite` は、`user` 主体なら作成者だけ。旧データは作成者が空なので、このままでは誰も書けない。ここを変える。
  - `session`・`reflection`: 組織メンバーで、かつ読めるもの(org・public)。共有ログインの書き方と同じ。private は今までどおり作成者だけ。
  - `roadmap`・`race`・`minutes`: 組織メンバーなら書ける。
  - `voice`: 今までどおり作成者だけ。
- 書き込みは表示中の組織に対してだけ行う。所属していても表示中でない組織のものは、旧 API からは書き換えない。
- 練習の削除(`DELETE /api/projects/:name`)も、表示中の組織のメンバーならできる。今の `canDeleteDay` の条件(器の中身を全部書けるときだけ)は残す。
- 今は `isCompatWriter` が `legacy` の共有ログインだけを書き手と認めている。これを、「表示中の組織のメンバーであるアカウント」も書き手と認めるように広げる。書き込み系の旧 API(`PUT/DELETE /api/projects/*`・`PUT /api/overlays/*`・`POST /api/sensor-imports`・`POST /api/minutes-imports/commit`・アップロード)すべてが対象。

### 5.5 新しく作るものの所属

- 新しい器(練習日)は、表示中の組織に属する(`practice_days.org_id`)。今の `putProject` は `s.orgId`(= `MIGRATION_ORG_ID`)を使っているので、アカウントの主体では表示中の組織を使う。
- 新しい反省・ロードマップの行の所有者のカラム(`reflections.author_user_id`・`roadmaps.user_id`)は、共有ログインで作ったときと同じく **NULL のままにする**。公開範囲の既定は `org`。(設計者の判断)
  - 理由: このカラムは「書いた人」ではなく「誰についてのデータか」を表している。名簿照合(`accountsRepo.reattachLegacy`)が `legacy_name`・`legacy_author_name` から本人に付け替えるのに使う。書き手を入れると、困ることが3つある。
    - `roadmaps.user_id` の UNIQUE 制約に違反しうる。
    - `syncRoadmaps` が付け替え済みの行とみなし、PUT で消さなくなる。
    - 議事録取込みで作った他人の反省が、取込んだ人のものになる。
  - 書き換えは組織メンバー全員ができる(§5.4)ので、所有者が空でも困らない。
  - 「誰が書いたか」を残したくなったら、別のカラムを足す別の作業にする。

### 5.5.1 練習は ID で見分ける。名前は重複してよい

利用者の決定: **練習の名前は重複可能にして、練習 ID で見分ける。**

- 練習 ID は `practice_days.id`(`pd_…`)。サーバーが付ける。
- 名前(`practice_days.legacy_name`、今は `sailviz-YYYYMMDD-HHMM.sailviz.json` の形)は表示用になる。同じ組織の中でも重複してよい。`001_data.sql` の `legacy_name TEXT UNIQUE` を外すマイグレーションを足す(SQLite は制約を外すのに表の作り直しが要る)。
- 旧 API の形を次のように変える(Web をあわせて直す)。
  - `GET /api/projects`・`GET /api/summaries`: 要素に `id` を足す。`name`・`label` は今までどおり。
  - `GET/PUT/DELETE /api/projects/:id`: パスは名前ではなく練習 ID。
  - 新しい練習は `POST /api/projects`(本文は練習の JSON)で作り、`{ id }` を返す。作成先は表示中の組織。
  - 議事録取込み(`/api/minutes-imports/commit`)・センサー取込みなど、練習を名前で指していた所も ID にする。
- ファイル版(`STORAGE=file`、本番)では、ファイル名をそのまま ID として返す(`id === name`)。ファイル版の動きは変えない。
- 取込み(`importFromFiles`)が同じファイルを二重に入れないための突き合わせ(`legacy_name`)は残す。
- sailviz-field の最新版(`origin/main`)は旧 API を使っていないので、この変更の影響を受けない。

### 5.6 全体目標とロードマップを組織ごとにする

- 今の `roadmaps` 表は、`legacy_name`(人名、または `__team__`)だけで行を突き合わせている(`server/db/roadmapSync.js`・`dbRepo.writeOverlay`)。このままだと、組織が違っても `__team__` が 1 行になる。人名が組織間で重なった場合も同じ。
- **突き合わせを (組織, 名前) の組にする。** 組織 A の `__team__` と組織 B の `__team__` は別の行になる。
- ロードマップの PUT(全置き換え)は、表示中の組織の行だけを置き換える。他組織の行には触らない(入力に無くても消さない)。
- 取込み(`importFromFiles`)・`fixLegacyOrgId`・既存の `syncRoadmaps` の動き(付け替え済みの `user_id`・`org_id` を保つ)は壊さない。

### 5.7 進捗・コメント

- 進捗 PUT(全置き換え)は、表示中の組織の反省に付いた項目だけを置き換える。他組織の項目は、入力に無くても消さない。
- 注意: 反省の ID は旧データでファイルをまたいで重複している(メモ「Track id not unique」)。進捗のキーは元の反省 ID なので、同じ ID が複数の組織の反省に当たることがありうる。その場合は「当たる反省がすべて表示中の組織にあるときだけ書ける」とする(今の `mergeProgressWrite` の `ts.every(...)` と同じ考え方)。

### 5.8 共有ログイン(書き込みトークン)

- 動きは変えない。`MIGRATION_ORG_ID` の組織を読み書きし、ヘッダーは無視する。
- 書き込みトークンの Cookie とアカウントの Cookie が両方あるときは、今と同じく書き込みトークンが優先する(`resolveIdentity`)。
- 閲覧ゲートの Cookie(`sailviz_view`)とアカウントの Cookie が両方あるときも、今の優先順位(閲覧ゲートが有効なら共有ログインを優先。`compatPrincipal.resolveSubject`)を変えない。(設計者の判断)
  - staging は閲覧ゲートが無効(起動ログが `view-gate=OFF`)なので、今回の切り替えには影響しない。
  - DB 版で閲覧ゲートを有効にすると、閲覧ログイン済みのアカウント利用者は共有ログインとして扱われ、組織の切り替えが効かない。この制限は残る。閲覧ゲートを止める時期(Phase 6)にあわせて見直す。

### 5.9 ファイル版(`STORAGE=file`)

- 組織の概念が無いので、今のまま(本番 `sailviz-sit` はファイル版で動いている)。ヘッダーは無視する。

### 5.10 新 API と sailviz-field

- sailviz-field(`/Users/reimurase/Documents/sailviz-field`)は設計書 v2 の新 API を使う。練習は `practiceDayId` で見分けている。新 API はサーバーにまだ無い(移行計画 Phase 3〜5)。
- sailviz-field にも、表示中の組織を選ぶ仕組みを入れる(別の指示で sailviz-field 側で作業する)。所属が 1 つなら選ばせず、選んだ組織を覚え、全リクエストに `X-Sailviz-Org` を付ける。
- サーバーが新 API を作るときの約束:
  - 組織で絞る読み取り(例: `GET /api/practice-days?scope=org`)は、表示中の組織だけを返す。
  - 練習日を探す・作る処理(例: `PUT /api/me/reflections/:id` が練習日から器を決める)は、表示中の組織の中で探し、無ければ表示中の組織に作る。
  - ヘッダーが無ければ所属組織の先頭、所属していない組織なら 403(§5.2 と同じ)。
  - 自分のもの(`scope=mine`、自分の声の反省など)は組織で絞らない。

## 6. 実装者に任せること

- `localStorage` のキー名。
- 組織管理画面のボタンの見た目と配置。表示中の組織であることの示し方。
- ホーム画面などに「今どの組織を表示しているか」を出すかどうか。出すなら組織管理へのリンクにする。
- 主体の表し方(`user` に `activeOrgId` を足すか、新しい種類の主体にするか)。ただし `policy.js` は純関数のまま保つ。
- `roadmaps` を (組織, 名前) で突き合わせるために、マイグレーション(例: `(org_id, legacy_name)` の一意制約)を足すかどうか。足すなら、既存データ(staging の 2 行)で問題が出ないことを確かめる。
- `/api/auth`(Web が書き込みできるかを見る)の返し方。今の Web は編集モードを廃止して書き込み要素を常に有効にしている(`applyEditableState`)ので、変えなくても動く見込み。
- テストの組み方。既存の TDD の流儀(`node --test`、Node 24)に合わせる。

## 7. 確認方法(完了条件)

- 2 組織に入ったアカウントで、組織を切り替えると、ホームの全体目標と練習一覧が切り替わる。
- そのアカウントで、表示中の組織の全体目標・練習・反省・進捗を保存でき、もう一方の組織のデータは変わらない。
- 1 組織だけのアカウントには切り替えボタンが出ず、保存できる。
- 書き込みトークンでの読み書きが今までどおり動く(既存の互換 API のテストが通る)。
- 所属していない組織の ID をヘッダーに付けると 403 になる。
- 2 つの組織に同じ名前の練習があっても、それぞれ ID で開け、保存しても他方が変わらない。
